## 3. Критично

### C-1 🔴 План инструментов без лимита длины блокирует инстанс целиком

**Где:** `packages/api-server/src/routes/assistant.ts:100`, `packages/agent-tools/src/tools.ts:405`

Обработчик `POST /api/assistant` тщательно ограничивает всё, кроме главного:

```ts
MAX_ASSISTANT_MESSAGE_CHARS = 12_000   // ✅ сообщение
MAX_HISTORY_ITEMS = 12                 // ✅ история
MAX_ASSISTANT_CONTEXT_CHARS = 1_000_000 // ✅ XML и граф
const tools = Array.isArray(req.body?.tools) ? req.body.tools : undefined; // ❌ длина не проверяется
```

`parseToolPlan()` валидирует каждый элемент, но никогда — длину массива.
`constrainToolPlan()` только отфильтровывает collaboration-инструменты.
Ветка с `tools` **не требует ключа LLM** (`hasTools` пропускает проверку `configured`) — то есть
доступна любому вошедшему через Google пользователю без каких-либо внешних зависимостей.

**Измерено на живом инстансе:**

| Шагов в плане | Размер тела | Время ответа | Статус |
|---|---|---|---|
| 1 000 | 47 КБ | **13.8 с** | 200 |
| 4 000 | 188 КБ | **> 120 с** (не дождался) | — |

Во время выполнения плана на 4 000 шагов `GET /api/health` **не ответил за 15 секунд**:
event-loop заблокирован полностью, инстанс не обслуживает никого.

Оба тела на порядок меньше лимита `express.json({ limit: '2mb' })`.

**Почему таймаут не спасает.** `assistantTimeoutMs()` (50 с) реализован через `setTimeout` +
`Promise.race`. `executePlanBestEffort()` — синхронный цикл; пока он крутится, таймер не может
сработать, а `Promise.race` не вытесняет синхронный код. Дедлайн, ради которого написан
комментарий «keep the application timeout below Vercel's 60 second function ceiling», на этом
пути не действует.

**Умножение эффекта.** `createAssistantRequestGate` разрешает 2 одновременных и 30 запросов в
минуту на пользователя. Один аккаунт: 30 × 13.8 с ≈ **414 с CPU в минуту на инстанс**.

**Влияние.** Отказ в обслуживании всего инстанса одним аутентифицированным пользователем;
на Vercel — сожжённый бюджет функции (60 с) и платформенный таймаут вместо структурированного
504. Плюс `inverse: () => structuredClone(prev)` удерживает по полному снимку графа на каждый
шаг — для длинного плана это ещё и рост памяти.

**Что сделать (по возрастанию стоимости):**
1. Ограничить длину плана в маршруте (`MAX_TOOL_PLAN_STEPS`, порядка 50) → 413 при превышении.
   Одна строка, снимает вектор целиком.
2. Проверять `signal.aborted` внутри цикла `executePlanBestEffort` и уступать event-loop между
   шагами (`await new Promise(setImmediate)` каждые N шагов), чтобы 50-секундный дедлайн работал.
3. Долгосрочно — устранить квадратичность (см. H-3).

## 4. Высокий приоритет

### H-1 🟠 Тело больше лимита → 500 вместо 413

**Где:** `packages/api-server/src/app.ts:54-58`

Обработчик ошибок распознаёт только ошибку парсинга:

```ts
const parseFailed =
  (err instanceof SyntaxError && 'body' in err) ||
  (err as { type?: string }).type === 'entity.parse.failed';
```

`entity.too.large` (413 от body-parser) сюда не попадает и падает в общий 500.

**Воспроизведено:**
```
POST /api/processes с bpmnXml на 3 МБ
→ 500 {"error":"Internal server error","requestId":"626cd0f5-…"}
```

**Влияние.** Двойное: пользователь видит «внутренняя ошибка» вместо «файл слишком большой», а в
`stderr` пишется `request_failed` с уровнем `error` — это ложная тревога в мониторинге, которую
может вызвать любой пользователь.

**Фикс:** добавить ветку `type === 'entity.too.large'` → `413 { error: 'Request body is too large' }`.

### H-2 🟠 Три несогласованных лимита размера BPMN

| Лимит | Значение | Где |
|---|---|---|
| Клиентский импорт | 8 МиБ | `import-xml.ts:6` `MAX_BPMN_IMPORT_BYTES` |
| Валидация домена | 2 МиБ | `validateProcess.ts:9` `PROCESS_BPMN_XML_MAX` |
| Тело HTTP | 2 МБ | `app.ts` `express.json({ limit: '2mb' })` |

Файл на 3 МБ проходит клиентскую проверку (`readBpmnFile`), парсится в браузере, попадает в
`POST /api/processes` — и умирает на транспортном уровне с 500 (H-1). Доменный лимит в 2 МиБ
недостижим в принципе: конверт JSON всегда упирается в лимит тела раньше.

**Фикс:** один источник истины. Выровнять клиентский лимит по серверному (или поднять лимит тела
для маршрутов процессов) и проверять `file.size` против того же значения.

### H-3 🟠 Каждая семантическая операция клонирует весь граф дважды

**Где:** `packages/semantic-core/src/ops.ts:29-34`

```ts
function apply(prev, fn) {
  const draft = structuredClone(prev);        // клон #1
  const id = fn(draft);
  rebuildStructure(draft);                    // полный ре-детект регионов
  return { process: draft, inverse: () => structuredClone(prev), id }; // клон #2 (в замыкании)
}
```

**Измерено** (одна операция `addTask` на графе растущего размера):

| Узлов в графе | Одна операция |
|---|---|
| 52 | 0.34 мс |
| 102 | 0.65 мс |
| 202 | 1.27 мс |
| 402 | 3.76 мс |
| 802 | **13.06 мс** |

Рост суперлинейный: клон O(n) + `rebuildStructure` (доминаторный анализ) O(n) на каждую правку.
Последовательность из n операций → O(n²)+.

**Влияние.** Это корень C-1, но задевает и обычную работу: на диаграмме в ~800 узлов каждое
действие в редакторе (добавить задачу, переименовать, соединить) стоит ~13 мс только внутри ядра,
до layout и рендера. Плюс каждая операция удерживает полный снимок `prev` для undo.

**Фикс:** инкрементальный `rebuildStructure` (пересчитывать только затронутый scope) и ленивый
inverse (хранить дельту, а не клон). Оба изменения локальны в `ops.ts`/`detect.ts`.

### H-4 🟠 Двойной парсинг XML на каждом сохранении

**Где:** `packages/api-server/src/services/processService.ts:264-266`

```ts
await importBpmnXml(bpmnXml);      // → xmlToProcess() — полный разбор moddle
return await bpmnToWorkflow(bpmnXml); // → xmlToProcess() ещё раз, тот же документ
```

`bpmnToWorkflow` (`workflow.ts:122`) внутри снова вызывает `xmlToProcess(bpmnXml)`.

**Измерено:**

| Узлов | XML | `importBpmnXml` | `bpmnToWorkflow` | Итого на сохранение |
|---|---|---|---|---|
| 12 | 7 КБ | 9 мс | 14 мс | 23 мс |
| 102 | 60 КБ | 26 мс | 32 мс | 58 мс |
| 302 | 180 КБ | 48 мс | 56 мс | **104 мс** |

Автосохранение срабатывает по debounce 800 мс, то есть эти ~100 мс синхронного CPU повторяются
при активном редактировании постоянно.

**Фикс:** `importBpmnXml` уже возвращает `{ xml, process }` — использовать этот `process` для
проекции workflow вместо повторного разбора. Экономия ~50 % стоимости записи, изменение
в одной функции.

## 5. Средний приоритет

### M-1 🟡 Список процессов линтит каждую строку синхронно

**Где:** `processService.ts:167` (`toSummary`) — на каждую строку `lintProcess(row.bpmnXml)`, плюс
`xmlToProcess` для строк с collaboration-маркером, плюс `bpmnToWorkflow` если `workflowJson` пуст.

**Измерено:** список из 60 маленьких процессов — 45 мс (≈0.5 мс/строка), это нормально.
Но `lintProcess` на документе в 302 узла — **25.9 мс**. При `limit=100` (разрешённый максимум)
и реальных диаграммах это ~2.6 с полностью синхронного CPU на один `GET /api/processes`.
`Promise.all` здесь не помогает: `lintProcess` синхронный.

**Фикс:** кешировать сводку (`quality`, `structure`, `preview`) в колонке при записи — она и так
пересчитывается на каждом сохранении — и отдавать список без разбора XML.

### M-2 🟡 `POST /api/processes/:id/template` обходит оптимистическую блокировку

**Где:** `packages/api-server/src/routes/processes.ts:153-166`

```ts
const current = await getProcessById(req.params.id, ownerId(req));
const updated = await updateProcess(req.params.id, { bpmnXml: body.bpmnXml, version: current.version }, …);
```

Версия читается прямо перед записью — это last-write-wins с окном гонки, тогда как весь остальной
API строго требует версию от клиента. Побочный эффект в UI: «Сохранить как шаблон» поднимает
`version` мимо очереди сохранения, и следующий отложенный PATCH получает 409 — пользователь видит
диалог конфликта на ровном месте.

**Фикс:** принимать `version` в теле запроса и передавать её, как делают остальные маршруты.

### M-3 🟡 Холодный старт делает full scan и лишний парсинг

**Где:** `packages/api-server/src/seed.ts:13`, вызывается из `api/index.ts` на первый запрос каждого инстанса.

```ts
const rows = await db.select(…).where(sql`trim(${table.bpmnXml}) = ''`);  // full scan, не sargable
const workflowJson = JSON.stringify(await bpmnToWorkflow(DEFAULT_BPMN_XML)); // ~14 мс всегда, даже если rows пуст
```

Плюс сама `migrate()` выполняет DDL (`ALTER TABLE … IF NOT EXISTS`) на каждом холодном старте.
GAPS.md уже фиксирует «cold-start migrations/repair» как долг — уточнение: скан не индексируем,
а парсинг шаблона выполняется безусловно.

**Фикс:** перенести починку в одноразовую миграцию; `bpmnToWorkflow` вызывать только при `rows.length > 0`.

### M-4 🟡 Обратная связь не имеет жизненного цикла

**Где:** `feedbackService.ts:109` — `listFeedback` всегда фильтрует `status = 'new'`.
Маршрутов на изменение статуса нет (полный инвентарь — 21 маршрут, ни одного `PATCH /api/feedback/:id`).
Значения `'reviewed' | 'resolved'` в типе и колонке мертвы.

**Влияние.** Владелец инбокса (`FEEDBACK_INBOX_EMAIL`) не может ничего разобрать: список только
растёт, обработанное не скрывается. Функция становится непригодной по мере роста.

**Фикс:** `PATCH /api/feedback/:id` со сменой статуса (только владелец инбокса) + фильтр в UI.

### M-5 🟡 `email_verified` запрашивается, но не проверяется

**Где:** `packages/api-server/src/auth/google.ts:33` — поле объявлено в типе `UserInfoResponse`
и приходит в ответе, но `exchangeGoogleCode` его не читает.

Значимо потому, что `isFeedbackInboxOwner()` выдаёт привилегию по строковому совпадению e-mail.
Для обычных Google-аккаунтов адрес всегда подтверждён, но полагаться на это неявно не стоит —
поле уже под рукой.

**Фикс:** `if (profile.email_verified === false) throw new Error(...)` в `exchangeGoogleCode`.

### M-6 🟡 `tokens:check` не выполняется в CI

`pnpm check` = `tokens:check && lint && typecheck && test:coverage && build`, но job `quality`
в `.github/workflows/ci.yml` запускает только `lint`, `typecheck`, `test:coverage`, `build`.
Сгенерированный `tokens.css` может разойтись с `tokens.json` в `main`, и ни один воркфлоу этого
не заметит. Сейчас он синхронен — проверено, — но гарантии нет.

**Фикс:** добавить шаг `pnpm tokens:check` в job `quality` (или заменить четыре шага на `pnpm check`).

### M-7 🟡 Ограничитель аутентификации: один бюджет на шесть эндпоинтов

**Где:** `routes/auth.ts:81` — один `authRateLimit` (60 запросов / 10 мин по IP) навешен на
`/status`, `/me`, `PATCH /me`, `/google`, `/google/callback`, `/complete`, `/logout`.

`AuthGate` дёргает `/api/auth/status` при каждой загрузке приложения. За общим NAT (офис, оператор
мобильной связи) 20 пользователей × 3 загрузки исчерпывают бюджет — и получают 429 **на самом
входе**, включая OAuth-callback. Хранилище — в памяти процесса, то есть в serverless лимит и так
работает лишь частично (это честно задокументировано для Architect-гейта, но не для auth).

**Фикс:** вынести читающий `/api/auth/status` из-под лимитера (или дать ему отдельный, более
свободный бюджет), а строгий лимит оставить на `/google`, `/complete`, `PATCH /me`.

## 6. Низкий приоритет

**L-1 — подавление CVE без принуждения.** `pnpm.auditConfig.ignoreCves: ["CVE-2026-56876"]` в
`package.json` действует на все прогоны `pnpm audit`, включая CI-шаг `audit:deps` — то есть даже
если пакет когда-нибудь попадёт в production-граф, ворота не сработают. `osv-scanner.toml`
содержит грамотную оценку риска и срок `ignoreUntil = 2026-11-20`, но **ни один workflow не
запускает osv-scanner**, поэтому срок никогда не «выстрелит». Сам риск сейчас нулевой:
`pnpm audit --prod` — чисто, `extract-zip` доступен только через `@lhci/cli → lighthouse →
puppeteer-core`. Проблема процессная.

**L-2 — поиск теряет спецсимволы.** `likePattern()` (`processService.ts:295`) вырезает `\ % _`
вместо экранирования. Проверено: `GET /api/processes?q=%25` возвращает **все** записи (паттерн
вырождается в `%%`). Поиск по «50%» или «snake_case» молча даёт неверный результат.
Фикс: экранировать через явный `ESCAPE '\'`.

**L-3 — нет составного индекса.** `processes_user_id_idx` и `processes_updated_at_idx` отдельные,
а основной запрос — `WHERE user_id = ? ORDER BY updated_at DESC`. Нужен `(user_id, updated_at)`.
Аналогично для `feedback` — запросы фильтруют по `(user_id, status)`, индекса на `status` нет.

**L-4 — бюджет бандла почти исчерпан.** `ProcessEditorPage-*.js` = 699 260 Б при лимите 720 000 Б
(97 %). Следующая заметная зависимость в редакторе упрётся в ворота. Тяжёлые экспортные
библиотеки (`jspdf`, `svg2pdf`, `html2canvas`) корректно загружаются динамически — это уже сделано
правильно, запас нужно искать в самом чанке редактора.

**L-5 — просроченные сессии не собираются.** `readSession` удаляет строку только при попытке её
прочитать, `createSession` — только для того же `userId`. Сессии ушедших пользователей живут
вечно. Нужен периодический `DELETE FROM sessions WHERE expires_at < now()`.

**L-6 — CSP только на уровне Vercel.** Полный набор заголовков есть в `vercel.json`, а
`operationalHeaders()` (`app.ts:22`) ставит `nosniff`, `Referrer-Policy`, `X-Frame-Options`,
`Permissions-Policy` — **без CSP**. Проверено на живом инстансе: в ответе CSP отсутствует.
Любое развёртывание не на Vercel (`pnpm start`) остаётся без CSP.
Отдельно отмечу: собранный `index.html` не содержит инлайн-скриптов, то есть строгий
`script-src 'self'` совместим с бандлом — перенос CSP в приложение безопасен.

**L-7 — `X-Forwarded-Host` без allow-list.** Проверено:
`curl -H 'X-Forwarded-Host: evil.example' /api/auth/status` → в ответе
`"callbackUrl":"https://evil.example/api/auth/google/callback"`. Эксплуатации через браузер нет
(заголовок кросс-доменно не подделать), а `isSafeRelayOrigin` закрывает relay-путь: по коду
подделанный `returnOrigin` отвергается с 400 (живьём не проверить без настроенного OAuth).
Тем не менее в production стоит явно задавать
`AUTH_BASE_URL`, чтобы `publicOrigin()` не зависел от заголовка вовсе.

**L-8 — обработчик колеса держит уничтоженный canvas.** В `BpmnEditor.tsx` эффект с колесом имеет
зависимости `[simulating]`, но захватывает `canvas` из `modelerRef.current` на момент запуска.
Эффект создания модельера пересоздаёт его при смене `processId`, а этот — нет; после смены
процесса без размонтирования панорамирование колесом тихо перестаёт работать (`viewbox()` кидает,
исключение проглатывается). Фикс: брать `modelerRef.current?.get('canvas')` внутри обработчика.

**L-9 — 8.9 МБ генерируемых артефактов в git.** `graphify-out/graph.json` (2.8 МБ),
`graphify-out/2026-08-18/graph.json` (3.3 МБ), `graphify-out/2026-08-22/graph.json` (2.8 МБ),

**L-10 — мелочи в подаче.** В `README.md:38` и `:42` литеральные `\n` внутри markdown-таблицы —

## 7. Что сделано хорошо (проверено, не на веру)

Это заметно выше среднего уровня для проекта такого размера:

- **Изоляция арендаторов.** Проверено вживую: пользователь B получает 404 (не 403) на чтение,
  изменение и удаление процесса пользователя A. Все запросы скоупятся по `user_id` на уровне
  сервиса, а не маршрута. Есть E2E-тест на это же.
- **Оптимистические блокировки.** CAS-предикат по версии в `UPDATE … WHERE version = ?` с
  честной проверкой `changed.length === 0` и повторным чтением — редко встречающаяся аккуратность.
  Проверено: PATCH без версии → 400, с устаревшей → 409 + `currentVersion`.
- **Аутентификация.** Токен сессии хранится как SHA-256 от `secret:token`; OAuth-state подписан
  HMAC и сверяется `timingSafeEqual`; relay-происхождения проверяются по строгому allow-list
  (одна метка вместо `*`); handoff-токен одноразовый с TTL 60 с; `SESSION_SECRET` fail-closed в
  production. Тестовый эндпоинт структурно не регистрируется при `NODE_ENV=production`.
- **CSRF.** Заголовок `X-BPMN-CSRF: 1` + `Sec-Fetch-Site` + `Origin`. Проверено: без заголовка 403,
  с чужим `Origin` 403, безопасные методы проходят.
- **Валидация входа.** `page=0`, `limit=101`, `sort=drop` → 400 с внятным текстом. HTML вместо
  BPMN → 400 с кодом `html` и человеческим сообщением. Попытка prototype pollution через
  `__proto__` в теле PATCH не проходит (allow-list ключей).
- **Отсутствие XSS-стоков.** Ни одного `dangerouslySetInnerHTML`, `innerHTML`, `eval`,
  `new Function` во всём первокоде.
- **Секреты.** В собранном бандле нет ни одного упоминания серверных ключей. `.env.example`
  документирует почти все переменные, включая relay-паттерны и предупреждение про `VITE_`
  (не хватает только `SQLITE_PATH` и `NVIDIA_BASE_URL`).
- **SSRF-защита в AI-клиенте.** `nvidiaBaseUrl()` пиннится на `integrate.api.nvidia.com`, отвергает
  креды/query/hash в override, локальный хост разрешён только при `NODE_ENV=test`.
- **Очередь сохранения** (`processSaveQueue.ts`) — журнал в localStorage, экспоненциальный
  backoff только на 5xx, отдельная ветка offline, честное «recovery storage unavailable», когда
  запись в localStorage не удалась, guard на `beforeunload`. Сделано вдумчиво.
- **CI.** 4 job'а (quality / database с реальным Postgres / e2e desktop+mobile / lighthouse),
  все action'ы пришпилены по SHA, permissions сужены, CodeQL `security-extended`, gitleaks,
  OpenSSF Scorecard, Dependabot с группировкой. E2E реально проверяет a11y (axe, wcag21aa),
  визуальные регрессии и изоляцию арендаторов.
- **Гигиена кода.** 0 предупреждений линтера, ни одного `@ts-ignore`, ни одного `TODO`/`FIXME`
  в первокоде, 7 обоснованных `eslint-disable`. 752 теста, покрытие 77.79 % при пороге 60 %.
- **Документация честная.** `GAPS.md` прямо называет открытый долг (bpmn-js fallback, полный
  relayout, cold-start миграции, отсутствие глобальной квоты) вместо маркетинга. Проверенные
  утверждения README о E2E (a11y, визуал, изоляция) соответствуют коду.
